# AGENTS.md — ABIX Agent Instructions

You are working on **ABIX**, an ABI semantic layer and native ABI toolchain.
ABIX treats the native ABI as an explicit, machine-readable, verifiable
engineering artifact.

This file is the **project constitution** for AI agents. It is deliberately
short and behavioural. It answers *how to work here*, not *how the code works*.
Detailed knowledge lives in the documents listed under
[Documentation Authority](#documentation-authority).

Before modifying code, understand that ABIX has distinct layers:

* ABIX ABI semantic model — what an ABI *is*
* ABIX IR — the language-independent representation
* ABIX Runtime — consumes ABI, keeps execution native
* AMC — the ABI toolchain (extract / project / compare / generate)
* language frontend / plugin — maps one language AST onto ABIX IR
* serialized `.abix` — the canonical artifact

Do not collapse these layers unless the architecture explicitly requires it.

---

## 1. Project Principles

These are architectural constraints, not suggestions.

### 1.1 One source of ABI truth

```text
Language AST
    ↓
AMC / Language Adapter
    ↓
ABIX IR
    ↓
.abix / Runtime projection
```

The runtime may project or cache ABI information, but must **not** independently
redefine ABI semantics. When changing ABI-related behaviour, read
[`ABI-SPEC.md`](ABI-SPEC.md) and [`ARCHITECTURE.md`](ARCHITECTURE.md) first.

### 1.2 ABIX is not a VM

ABIX must not turn compatible native calls into an interpreter or generic
dispatcher. The intended model is:

```text
ABI discovery → ABI verification → binding / adaptation → native execution
```

Do not introduce a permanent runtime dispatch layer for calls that can be
executed directly through the native ABI.

### 1.3 ABIX is not a universal object model

ABIX describes existing native types and binary contracts. It does not define a
universal object hierarchy, ownership runtime, garbage collector, VM, or
replacement for C++/Rust/C. Do not add such abstractions to make
implementation easier.

### 1.4 Runtime and IR stay separate

ABIX IR represents ABI semantics; runtime structures are **projections** of that
model. Prefer `ABIX IR → runtime projection` over an independent runtime type
system.

### 1.5 Preserve the native fast path

Dynamic work belongs at discovery, binding, verification and adaptation
construction — not in every compatible call. Before adding hot-path runtime
overhead, check whether it can instead be done at binding time, generated by
AMC, cached, or represented as static metadata.

### 1.6 C++ is the first implementation, not the semantic boundary

Avoid putting C++-specific semantics into ABIX IR unless they represent a
genuine ABI concept. Language-specific behaviour belongs in a
[language plugin](LANGUAGE-PLUGIN.md), not in the core model.

## 2. Repository Orientation

```text
abix/    ABI model + runtime (header-only registry, descriptors, adapter)
amc/     AMC: core/ (ELF/Mach-O reader, metadata, adapter, symbol store, query, verify),
           cpp/ (Clang frontend+backend), dump/, mcp/
test/    runtime + unit tests (Catch2)
bench/   benchmarks
aue/     experimental Lua boundary layer + differential conformance
tools/   helper scripts (MCP demo, token cost, LLDB command, ELF test)
docs/    specification and design
```

### Key subsystems

| Subsystem | Location | Responsibility |
|-----------|----------|----------------|
| ABI model | `abix/` | `TypeDescriptor`, `FieldDescriptor`, `RuntimeRegistry`, `TypeTraits`, adapter dispatch |
| ELF/Mach-O reader | `amc/core/amc_elf.h` | Minimal ELF64 + Mach-O section reader (`is_binary`, `find_binary_section`, `read_binary_sections`) |
| Metadata Region | `amc/core/amc_metadata.h` | Self-describing, pointer-free metadata image (manifest + desc + hash + names) |
| ABI adapter | `amc/core/amc_adapter.h` | `generate_adapter()` — field-level mapping from source to target memory |
| Symbol store | `amc/core/amc_symbol_store.h` | Offline symbol resolution from `.abix` / Metadata Region |
| MCP server | `amc/mcp/` | AI-agent tool surface (`amc-mcp` binary) |
| LLDB plugin | `amc/dump/` | C++ LLDB plugin (`libabix_lldb.so`) |
| Versioned registry | `abix/runtime_registry.h` | `RuntimeRegistry::register_module(module, version)` — same TypeID across versions |

Read [`README.md`](../README.md) for orientation, then the documents relevant to
your change.

incorrect unless the specification is intentionally being changed.

## 4. Change Classification

Classify the change before editing and update the corresponding documents.

### A. ABI semantic change

Type identity, layout identity, calling convention, ownership, compatibility
rules, `.abix` representation.

Required: `ABI-SPEC.md`, `ARCHITECTURE.md`, tests, explicit compatibility
consideration.

### B. IR change

New IR record/field, normalization rule, canonical encoding.

Required: `ABI-SPEC.md`, IR + serialization tests. Do not add an IR concept just
because one source language has it.

### C. Runtime change

Registry, binding, loading, synchronization, caching, mapping.

Required: `ARCHITECTURE.md`, `docs/runtime.md`; benchmarks when
performance-sensitive. Do not leak runtime details into the ABI specification.

### D. AMC change

CLI command, AST extraction, ABI generation, code generation, diagnostics,
frontend integration.

Required: `docs/amc.md`, `LANGUAGE-PLUGIN.md` when the plugin boundary changes.

### E. Language plugin change

Follow [`LANGUAGE-PLUGIN.md`](LANGUAGE-PLUGIN.md); keep language-specific
behaviour out of the core model.

### F. Documentation / tooling / test-only change

Keep it scoped; do not change ABI semantics as a side effect.

## 5. Before Coding

For non-trivial tasks:

1. Read the relevant spec/architecture document.
2. Search the existing implementation for the concept being changed.
3. Identify the existing source of truth.
4. Decide whether the change affects ABI compatibility.
5. Check existing tests and examples.
6. Prefer extending an existing abstraction over a parallel one.
7. Do not redesign unrelated components.

Do not rewrite large parts of the architecture unless explicitly requested.

---

## 6. Implementation Rules

Prefer: existing abstractions; small changes; explicit ownership; explicit ABI
semantics; compile-time generation; cached binding information; zero-copy where
ABI-compatible; measurable performance changes.

Avoid: unnecessary abstractions; duplicate metadata systems; generic runtime
dispatch; hidden ABI conversions; language-specific concepts in the core IR;
speculative infrastructure; new dependencies without justification.

Do not introduce a new abstraction merely because an existing one is
inconvenient.

---

## 7. Error Handling

Expected operational failures use the project's established error model. Do not
introduce exceptions into low-level expected-failure paths without checking the
existing design. Follow the surrounding subsystem's conventions.

CLI tools report failures through the unified `abix.error/1` envelope
(`--error-format json`); keep new error paths on that schema.

---

## 8. ABI Compatibility

Never assume source-level compatibility implies ABI compatibility. When changing
layout, field order/type, alignment, size, calling convention, parameter/return
types, ownership or symbol identity, consider compatibility explicitly.

If the change is intentional, add or update an ABI regression test.

## 9. Build & Testing

### Build

Configure and build using `build/<CMAKE_BUILD_TYPE>` as the output directory:

```bash
# Release build
cmake -B build/Release -DCMAKE_BUILD_TYPE=Release -G Ninja -S .
cmake --build build/Release --parallel

# Debug build (with optional AddressSanitizer)
cmake -B build/Debug -DCMAKE_BUILD_TYPE=Debug -DSANITIZER=asan -G Ninja -S .
cmake --build build/Debug --parallel

# Debug build (no sanitizer)
cmake -B build/Debug -DCMAKE_BUILD_TYPE=Debug -DSANITIZER=none -G Ninja -S .
cmake --build build/Debug --parallel
```

Additional CMake options (see `CMakeLists.txt`):

| Option | Default | Description |
|--------|---------|-------------|
| `-DBUILD_TESTING=ON` | ON | Build tests |
| `-DBUILD_BENCHMARKS=ON` | ON | Build benchmarks |
| `-DSKL_ABIX_DEVELOPMENT=OFF` | OFF | Enable development-only diagnostics |
| `-DSKL_ABIX_BUILD_DLL_VARIANTS=ON` | ON | Build cross-toolchain DLL variants |
| `-DAMC_BUILD=ON` | ON | Build AMC toolchain (requires Clang/LLVM) |

### Test & Run

```bash
# Run tests
ctest --test-dir build/Release --output-on-failure

# Or run directly
build/Release/bin/test_all

# Run benchmarks
build/Release/bin/bench_all
```

For AMC changes, also exercise the CLI manually. For ABI changes, verify
generation, serialization, deserialization, comparison, compatibility and
runtime behaviour.

`amc/tests/amc_integration_test.py` is the CLI integration suite;
`amc/tests/core_test.cpp` holds core assertions; `test/` uses Catch2.

Do not claim a test passed unless it was actually run.

## 11. Generated Code and ABI Artifacts

Do not hand-edit generated ABI artifacts. Change the source/specification and
regenerate. When generated output changes, verify it is reproducible
(`amc build` must produce a deterministic `.abix`).

---

## 12. Performance

Do not optimize from intuition when changing binding, registry lookup,
synchronization, metadata lookup, call paths or type mapping. Prefer benchmarks
(see `bench/`, `aue/abix-bench`, `tools/abix_token_cost.py`). A performance
optimization must not silently change ABI semantics.

---

## 13. Scope Discipline

Stay within the requested task. Do not rewrite unrelated code, rename unrelated
APIs, reorganize the repository without need, introduce a framework for a small
feature, or change the ABI specification to simplify implementation. If the
requested change conflicts with an architectural constraint, explain the
conflict before changing the constraint.
