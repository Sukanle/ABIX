## 1. 如何阅读本文

下文有两类陈述，二者不可互换：

| 类型       | 含义                                                                                                                                                              |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **实测**   | 由本仓库基准套件在本机产生；见 [`benchmark_zh.md`](benchmark_zh.md) §5，以及 `memory/windows-benchmark.md` §8 的按家族重跑。用 `python tools/run_bench.py` 复现。 |
| **架构性** | 描述该框架**做了什么**(间接调用、封送、反射、GC、生命周期记账)，**并非在本机实测**。下面没有任何一个框架被安装或基准测试。                                        |

即：ABIX 的代价是测量值；竞品的代价是机制描述 + 量级判断。比较按**成本层级**进行，而不是拿不可比的数字相减。

运行环境：Windows 11、i7-14700K(20 物理核、HT 关闭、Defender 实时防护关闭)、MSYS2 UCRT64 g++ 16.2.0、`Release`(`-O3 -DNDEBUG`)。

## 2. ABIX 被测量到的成本层级

这些是「调用进插件」可能落到的实测档位；任何框架的热路径都由其中若干组合而成。

| 层级                                                     | ABIX 基准                                           |                 ns/次 |
| -------------------------------------------------------- | --------------------------------------------------- | --------------------: |
| 直接调用(内联)                                           | `BM_DirectCall`                                     |                 0.093 |
| 经函数指针调用                                           | `BM_FunctionPointerCall`                            |                 0.092 |
| `std::function`                                          | `BM_StdFunctionCall`                                |                 0.757 |
| ABIX Interface，路径已缓存                               | `BM_Interface_CachedCall`                           |                 0.946 |
| ABIX Interface，每次查表                                 | `BM_Interface_ResolvePerCall`                       |                 1.680 |
| ABIX 调用，RCU 括号 + 直接调用(不复核)                   | `BM_ABIX_Call_Raw`                                  |                 1.551 |
| ABIX 读侧括号本身                                        | `BM_Domain_EnterExit_Instance` / `BM_EBR_EnterExit` |         0.539 / 0.527 |
| **ABIX `Function::operator()`(每次调用复核名字 + 签名)** | `BM_ABIX_Call`                                      |             **2.763** |
| 名字哈希(6 / 16 字符)                                    | `BM_Hash_Name_6ch` / `_16ch`                        |         1.959 / 5.218 |
| 符号查找：哈希索引 / 线性扫描(16K 项、uniform)           | `abix_lookup_cross_bench`                           |     14.753 / 1569.475 |
| 经索引解析(16K、RCU 括号开)                              | `abix_resolve_bench rcu_on`                         |                 6.473 |
| 同路径热重载                                             | `BM_Reload_SamePath`                                |               3,545.6 |
| a/b 交替重载                                             | `BM_Reload_AlternatingPaths`                        |              18,492.0 |
| 仅 `LoadLibrary` / 仅 `FreeLibrary`                      | `BM_Reload_LoadOnly` / `FreeOnly`                   |    36,829.7 / 6,194.2 |
| retire + synchronize(unload 的 RCU 部分)                 | `BM_Reload_RetireSync`                              |                  48.0 |
| 空域上的 EBR `synchronize()`                             | `BM_EBR_Synchronize`                                |                 6.390 |
| EBR 同步相位，1T → 20T                                   | `BM_EBR_SyncPhase`                                  |         6.4 → 2,831.3 |
| 回收 1 → 10,000 个退休节点                               | `BM_EBR_ReclaimBatch`                               |        77.0 → 322,323 |
| 10 → 100 万待处理节点时的宽限期                          | `BM_EBR_GracePeriod`                                |       100.4 → 125,000 |
| 原子 load / store / inc                                  | `BM_Atomic_*`                                       | 0.183 / 0.187 / 3.390 |

两个事实立刻成立，并框定其余全部讨论：

1. **间接调用的地板到处都是同一水平。** 指针调用 0.09 ns；ABIX 自己的 Interface 快路径(0.95 ns)与 `std::function`(0.76 ns)同档。没有哪个框架在「间接调用有多快」上赢或输。
2. **ABIX 的全部溢价是 2.67 ns/次** —— 完全复核的 `Function::operator()` 2.763 ns 对直接调用 0.093 ns，对自身的 `Call_Raw` 则是 +1.21 ns。这笔溢价正是热重载的代价：句柄每次调用都重新校验缓存的 image、名字哈希与签名，因此被换出的旧模块**永远不可能**被跳到。

## 3. 逐项对比

每一项给出：每次调用做什么、擅长什么、代价是什么、什么时候该选它。

### 3.1 COM

**机制。** 它是一个**二进制标准**而非库：vtable 布局 + `AddRef`/`Release` 生命周期 + 以 IID 为键的 `QueryInterface` 发现 + 注册表激活。在 ABI 层面语言中立，也是本文中**唯一**为「被无关语言消费」而设计的模型。

|                        |                                                                                                                                                                                                                                 |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 每次调用做什么(架构性) | 一次 vtable 间接调用；不做名字/签名检查(IID 就是那次检查，且只在 `QueryInterface` 时发生一次)                                                                                                                                   |
| ABIX 的对应档(实测)    | `BM_Interface_CachedCall` 0.946 ns——同为「缓存条目后间接调用」的形态。`Release()` 是一次 interlocked 递减，与 `BM_Atomic_Inc_U32` 3.390 ns 同档                                                                                 |
| 优点                   | Windows 上无处不在；语言中立；二进制契约稳定且有文档；有 apartment/封送模型可跨线程、跨进程                                                                                                                                     |
| 缺点                   | **没有热重载、没有 ABI 演进**：接口一旦冻结，加方法就要新 IID 并重编所有消费者；引用计数生命周期靠人工，泄漏/过早卸载是调用方的责任；注册表激活；apartment/进程不同时需封送                                                     |
| ABIX 的差距            | ABIX 不具备语言中立(只有 C ABI 表，由 C++ 消费)、没有注册表、没有 apartment 模型。但它有 COM 刻意不做的东西：基于 `retire` 的生命周期(没有引用计数可写错)、可校验的跨编译器 ABI、以及**让存活句柄在交换后继续调用新模块**的重载 |

**选 COM**：边界要被 Windows 上其它语言/VM 消费，且接口不会变。**选 ABIX**：插件本身会在运行中的宿主里被替换。

### 3.2 Qt

**机制。** 自带对象模型的 C++ 应用框架：`moc` 生成元对象表，信号/槽经 `QMetaObject::activate` 按索引派发，`Q_PROPERTY`/`Q_INVOKABLE` 提供反射，`QPluginLoader`加载的插件其 `QObject` ABI 必须与 Qt 构建匹配。

|                        |                                                                                                                                                                                   |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 每次调用做什么(架构性) | 按索引派发进元对象表 + QObject 记账；经元对象系统调用时还要 `QMetaType` 转换                                                                                                      |
| ABIX 的对应档(实测)    | ABIX 的表探测是 `abix_lookup_cross_bench`(16K 时 14.8 ns，zipf 6.3 ns)——两者唯一共享的步骤是「找到条目、再调用」                                                                  |
| 优点                   | 一整套应用框架(控件、事件循环、网络、model/view);源码级跨平台；工具链成熟(designer、翻译);插件的 ABI 在**同一 Qt 版本内**稳定                                                     |
| 缺点                   | **它不是 ABI 层**：Qt 的二进制兼容按 Qt 大版本 + 编译器/编译选项划分，升级 Qt 就要重建插件；信号/槽是源码级机制而非跨编译器契约；没有热重载；只为一条插件边界而引入整个运行时偏重 |
| ABIX 的差距            | ABIX 是边界，Qt 是应用。Qt 给你整个 App；ABIX 给你「在 App 内部换掉一个模块」的能力                                                                                               |

**选 Qt**做应用与 UI;**用 ABIX**(或纯 C ABI)做那部分必须熬过一次模块替换的逻辑。

### 3.3 Unity

**机制。** 托管运行时(Mono 或 IL2CPP)+ 以 C# 为创作语言；原生代码经`[DllImport]`/P-Invoke 到达，伴随参数封送与托管↔原生切换。

|                        |                                                                                                                                                                                        |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 每次调用做什么(架构性) | 托管 ↔ 原生切换、可选的参数/字符串封送，外加托管侧记账(GC、`MonoBehaviour` 反射/序列化)。IL2CPP 去掉了解释器，但没去掉封送与 GC                                                        |
| ABIX 的对应档(实测)    | 无——ABIX 没有托管边界。最接近的是 `BM_ABIX_Call` 2.763 ns，而那是**一次完整校验调用的全部成本**                                                                                        |
| 优点                   | 玩法代码迭代极快；资产/编辑器生态庞大；跨平台构建；GC 消除了大部分手工生命周期 bug；Burst/Jobs 做数据并行                                                                              |
| 缺点                   | **进入原生代码的方向很贵**(封送 + 切换，比 vtable 调用高若干数量级);GC 停顿；暴露给 C# 侧的 ABI 由运行时决定，不是 C++ 的；不提供原生热重载(脚本重载要么重载 domain，要么 IL2CPP 重编) |
| ABIX 的差距            | ABIX 不跑托管代码、不提供封送。换来的是：一次调用是纳秒而非一次切换，且卸载安全是显式的(`unload()` 在句柄存活时拒绝)，而不是交给 GC                                                    |

**选 Unity**：产品本身就是托管的游戏/仿真。

**选 ABIX**：原生宿主需要在没有托管边界的情况下加载、调用并替换原生模块。

### 3.4 Unreal Engine

**机制。** C++ + 生成的胶水：UHT 为 `UCLASS`/`UFUNCTION`/`UPROPERTY` 生成反射数据，`UObject` 由 GC 管理，Blueprint 调用走那层反射，迭代靠 Live Coding / Hot Reload 而不是插件 ABI。

|                        |                                                                                                                                                                                                         |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 每次调用做什么(架构性) | 原生对原生的 `UFunction` 调用接近普通 C++ 调用；凡是从 Blueprint 或经反射到达，就多一次反射派发与参数封送                                                                                               |
| ABIX 的对应档(实测)    | 原生对原生那一端：`BM_DirectCall` 0.093 ns / `BM_ABIX_Call` 2.763 ns。反射那一端 ABIX 没有对应物                                                                                                        |
| 优点                   | 完整引擎(渲染、物理、网络、编辑器);反射让编辑器能通用地驱动 C++ 类型；Live Coding 提供不重启的短迭代                                                                                                    |
| 缺点                   | `UObject` 布局与模块 ABI **不跨引擎版本稳定**——插件要随引擎重建；Live Coding 只补代码、不改布局，而 UE 的 "hot reload" 局限众所周知；反射/GC 层对对象模型是强制的，即你只想要一个函数指针也得付这层成本 |
| ABIX 的差距            | ABIX 的边界由**元数据内容**定版本并在加载/verify 时校验，句柄能熬过一次模块替换；UE 的边界是「同一引擎构建」                                                                                            |

**选 Unreal**：你就在它里面开发。**选 ABIX**：插件必须在已发布的宿主里不重启地替换，且你想要一个**可校验的 ABI** 而不是一次「构建匹配」。

### 3.5 相邻选项

| 选项                              | 模型                                 | 相对 ABIX                                                                                                                          |
| --------------------------------- | ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------- |
| **WebAssembly Component Model**   | 沙箱模块 + 接口类型化边界 + 生成绑定 | 隔离性与语言中立更强；付出边界/序列化成本并需要 wasm 运行时；ABIX 在进程内且零拷贝                                                 |
| **FlatBuffers / Protobuf / gRPC** | 经缓冲/管道/socket 传序列化消息      | 语言中立、可解耦版本；但每消息编解码成本远高于一次函数调用——这是**数据交换**问题，不是函数绑定                                     |
| **P/Invoke、ctypes、CFFI、JNI**   | 各语言自己的外部函数机制             | 与 ABIX 目标相同(调用原生代码)，但一次只覆盖一种绑定且需封送；ABIX 额外提供元数据校验、名字+签名表、哈希索引查找与可安全重载的句柄 |
| **libffi / 手写 vtable**          | 自己搭边界                           | 控制力最大，但没有元数据、没有校验、没有重载方案；ABIX 那 2.67 ns 溢价正是你本来要自己写的东西                                     |

## 4. 性能差距究竟在哪里

1. **每次调用的间接层：没有实质差距。** 指针调用 0.09 ns、缓存 Interface 0.95 ns、`std::function` 0.76 ns。在这个层面宣称热路径胜利的，量到的是自己的记账而不是调用。
2. **每次调用的校验：ABIX 是刻意付的。** 比裸调用多 2.67 ns。COM/Qt 不按次付这笔(它们校验一次，或从不校验)，因此它们也无法像 ABIX 那样熬过一次模块替换。
3. **托管/VM 边界：真正的数量级台阶。** P/Invoke、Blueprint 反射与封送是**切换**而非调用——最快也要几十到几百纳秒，一旦涉及反射或序列化就是微秒级，而 ABIX 是 2.76 ns。托管引擎插件与ABIX 的差距就在这里(一到三个数量级)，这是为 GC 与创作效率做的**自觉取舍**，不是缺陷。
4. **加载/卸载受 OS 支配，另加一笔很小的 RCU 税。** `LoadLibrary` 36.8 µs、`FreeLibrary` 6.2 µs，而 unload 的 RCU 部分(retire + synchronize)只有 **48 ns**——不到加载器成本的 1%。所有框架都要付加载器成本；ABIX 的宽限期安全并不是卸载昂贵的原因。
5. **热重载是各模型的分水岭。** ABIX：同路径 **3.5 µs**、a/b 交替 **18.5 µs**。Qt：按 Qt 版本重建插件。COM：新 IID、重建消费者。UE Live Coding：打补丁、不改布局、秒级循环。Unity：domain 重载或 IL2CPP 重编。
6. **并发记账是扩展性代价，而且看得见。** 空域 `synchronize()` 6.4 ns，但 `BM_EBR_SyncPhase` 在 20 线程时 2,831 ns(≈440×)：EBR 必须等所有活跃 epoch，因此「高频 + 多线程写侧」是 ABIX 最弱的轴。`ReclaimBatch`(1 → 10,000 节点：77 ns → 322 µs)同理。读者注册表条目也**永不删除**——曾经进入过的线程会带着 `epoch == 0` 一直留在扫描链表里，而**每一次**宽限期轮询都要遍历全部节点：约 3.4 ns/节点，即 10 线程时 12 ns，但 10,000 线程时**单次轮询 34 µs**，且该轮询位于自旋循环内。
7. **查找按设计是 O(1)。** 16K 项时：哈希索引 **14.8 ns** 对线性扫描 **1,569 ns**(106×,uniform)，zipf 下 6.3 对 36.7 ns(5.8×)。超过 `SKL_ABIX_HASH_THRESHOLD` 会在加载时建索引(64 项 77.8 ns → 16K 项 49.5 µs)，这也说明 16K 项模块的加载由**建索引**而非加载器支配。

## 5. 场景矩阵

| 场景                             | ABIX                              | COM             | Qt         | Unity      | Unreal               |
| -------------------------------- | --------------------------------- | --------------- | ---------- | ---------- | -------------------- |
| 宿主运行中可替换的原生插件       | **最合适**                        | 不可以          | 不可以     | 仅托管脚本 | 部分(Live Coding)    |
| 跨编译器/跨工具链原生边界        | **最合适**(元数据校验)            | 好(冻结 IID)    | 按 Qt 构建 | 不适用     | 按引擎构建           |
| 语言中立的消费者                 | 否(C ABI 表)                      | **最合适**      | 仅 C++     | C# 优先    | C++/Blueprint        |
| 严格单次调用延迟(读多、临界区短) | **最合适**                        | 好              | 好         | 跨界很差   | 原生好、Blueprint 差 |
| 多线程高频写侧                   | 弱(EBR 同步随线程数增长)          | 不适用          | 不适用     | 不适用     | 不适用               |
| 丰富应用面(UI、事件循环、资产)   | 无                                | 无              | **最合适** | **最合适** | **最合适**           |
| 沙箱/跨进程隔离                  | 否                                | 部分(apartment) | 否         | 否         | 否                   |
| 带 CI 校验的 ABI 演进            | **最合适**(`.abix`、`amc verify`) | 人工            | 人工       | 不适用     | 人工                 |
| 托管语言体验、GC                 | 否                                | 否              | 否         | **最合适** | 部分                 |

## 6. ABIX 不适用的地方

说清楚——只列优点的对比没有价值：

- **它是边界，不是平台。** 没有 UI、事件循环、资产管线、网络或脚本。需要这些就该用 Qt/Unity/Unreal，而 ABIX 至多是其中一小块。
- **仅 C++、无封送。** 类型必须 ABI 稳定(整数、指针、平凡结构体)。没有 IDL，没有复杂类型的自动转换，没有语言中立的对象模型。
- **推进权没有公平性保证。** 一直抢不到的写者会无界重试(F0)。可取消 FIFO 的方案存在但**刻意未实现**——100+ 个独立进程的压测未发现持续饥饿。
- **存在无保护的逃生通道，且已如实标注** `Function::raw()`、`Object::resolve()` 与闭包都不带读侧保护；被调方**不得让异常逃出调用**(括号在调用返回后才释放)。
- **`ForceLeak` 与逐入口 `reload_until()`/`unload_until()` 未实现。** 超时只会延迟退休 image(Safe)，不会泄漏。
- **读者注册表只增不减**，写侧成本随线程数增长(见 §4.6)。曾经调用过 `enter()` 的线程会在进程生命周期内保留一个节点，而每次宽限期轮询都要遍历全部节点：约 3.4 ns/节点，10 线程时 12 ns，10,000 线程时**单次轮询 34 µs**，另有每线程一次永不归还的分配。要把它变成有界需要固定容量槽位数组(见 [路线图「研究 / 实验」](../development/roadmap_zh.md#研究--实验))；目前 `stats().registered_threads` 让这一增长可观测。
- **没有跨进程/沙箱模式** 一切都在进程内，恶意插件不被隔离。
